# AGENTS.md

## Project context

This repository implements the React Native MVP described in `PROJECT_SPEC.md`.

Before making changes:

1. Read this file.
2. Read the relevant section of `PROJECT_SPEC.md`.
3. Inspect the existing implementation and tests.
4. State a short plan and the files likely to change.
5. Implement only the requested scope.

Do not silently expand the product.

## Package manager and platform

- Use npm only.
- Keep `package-lock.json`.
- Do not create `yarn.lock`, `pnpm-lock.yaml`, or Bun lockfiles.
- This is an Expo Router React Native project.
- Keep the Expo SDK and React Native versions generated by the selected Expo template.
- Use `npx expo install <package>` for Expo or native modules that require Expo-compatible versions.
- Use `npm install <package>` for pure JavaScript packages.
- Do not upgrade Expo, React Native, React, or navigation packages unless the task explicitly requests an upgrade.

## Commands

Use these checks before finishing:

```bash
npm run lint
npm run typecheck
npm run test:ci
npm run check
```

The final check should normally be:

```bash
npm run check
```

Report any check that could not be run and the concrete reason.

## TypeScript rules

- Keep `strict: true`.
- Do not add `any`.
- Prefer discriminated unions and explicit domain types.
- Validate untrusted input with Zod.
- Do not hand-edit `src/types/database.generated.ts`.
- Convert database rows to domain models inside feature modules before passing data to UI components.
- Avoid non-null assertions except at a validated boundary.

## Architecture rules

- `src/app` contains route components and route layouts only.
- Business logic belongs under `src/features`.
- Shared presentational components belong under `src/components`.
- Server state belongs in TanStack Query.
- Zustand is only for ephemeral client UI state.
- Route components should compose hooks and components; they should not contain large SQL-shaped queries or scheduling algorithms.
- Keep feature APIs, hooks, schemas, types, and tests close to the feature.
- Avoid circular feature imports.

## UI rules

- The house facade is the main visual focus.
- Keep controls minimal and touch-friendly.
- Use React Native primitives and `react-native-svg`.
- Do not add a UI framework unless explicitly approved.
- Use theme tokens instead of scattered literal values.
- Every interactive icon needs an accessibility label.
- Do not rely on color alone to communicate state.
- Respect reduced-motion preferences.
- Korean UI copy should be natural, short, and consistent.

## Supabase and security

- Never place a service-role key in client code or `EXPO_PUBLIC_*`.
- Treat every `EXPO_PUBLIC_*` value as public.
- Enable RLS before exposing a public table to the client.
- Prefer RPCs for multi-row or race-sensitive operations such as house creation and invite acceptance.
- Do not trust client-provided ownership, payment, member, or room-slot claims.
- Security-definer functions must use a fixed `search_path` and minimal privileges.
- Never return private schedule events or note bodies to unauthorized users.
- Do not log passwords, access tokens, refresh tokens, note bodies, or private event titles.
- Applied migrations are append-only. Create a new migration instead of rewriting history.

## Realtime rules

- Realtime events are not the sole source of truth.
- Revalidate relevant queries after reconnect.
- Subscribe only to the current house and relevant tables.
- Always remove channels on unmount, house change, and logout.
- Do not send high-frequency animation or timer state through Realtime Presence.

## Scheduling rules

- All timestamp storage uses `timestamptz`.
- Repeating schedule clock values use `time`.
- Interpret MVP repeating schedules in the house IANA timezone.
- Keep status resolution in a pure function.
- Include tests for overnight ranges, weekday rollover, overlap priority, manual expiry, and event precedence.
- Do not poll the server every second for countdowns or status changes.

## Testing rules

Add or update tests when changing:

- Effective status resolution.
- Schedule matching.
- Validation schemas.
- Security-sensitive API behavior.
- Component accessibility labels.
- Loading, error, or empty states.

A feature is not complete merely because the happy path renders.

## Scope restrictions

Unless the user explicitly changes scope, do not add:

- Chat
- GPS or location tracking
- 3D rendering
- Avatar movement
- Mini-games
- Real payments
- Public feeds
- Multiple simultaneous houses
- External calendar sync

For immediate move-in, keep real billing outside the MVP. Never simulate a verified purchase in production code.

## Change discipline

- Prefer small, reviewable patches.
- Do not mix unrelated refactors into a feature.
- Preserve existing public behavior unless the task changes it.
- Reuse existing components and patterns before adding abstractions.
- Remove dead template code when it conflicts with the project structure.
- Do not leave TODOs for required acceptance criteria.
- Do not hide failures with disabled lint rules, skipped tests, or broad type casts.

## Completion response

At the end of a task, report:

1. What changed.
2. Important files changed.
3. Commands run.
4. Test and check results.
5. Known risks or items deliberately left for the next phase.

Keep the summary factual. Do not claim a command passed unless it was actually run.
